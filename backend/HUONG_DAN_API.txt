HƯỚNG DẪN BÀI NGÀY 1 — QUẢN LÝ CA LÀM VIỆC VÀ LỊCH HẸN

1. Chạy backend

Mở terminal tại thư mục backend:
  npm install
  Copy-Item .env.example .env

Nếu đã có .env thì giữ nguyên, chỉ bổ sung AUTH_SECRET. Tạo một chuỗi ngẫu nhiên bằng:
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
Chép kết quả vào AUTH_SECRET trong .env. Không chia sẻ chuỗi này cho frontend.
Chạy MongoDB local (MongoDB 6.0 trở lên), kiểm tra MONGO_URI, sau đó:
  npm run dev

2. Quyền sử dụng và token thử nghiệm

Dự án ban đầu chưa có User, mật khẩu hoặc API đăng nhập. Bài này thêm middleware
kiểm tra token có chữ ký HMAC SHA-256, không thêm màn hình hay API đăng nhập.
Token này có định dạng payload.signature, KHÔNG phải JWT và không dùng jwt.io.
Script dưới đây chỉ dành cho người phát triển chạy ở terminal, token hết hạn sau 8 giờ.
Khi làm đăng nhập thật, server cần lấy role và doctorId từ tài khoản đã xác thực.

Tạo token admin:
  npm run token -- admin

Dùng token admin để gọi POST /api/doctors với JSON:
  { "name": "Nguyễn Văn An", "specialty": "Nội tổng quát" }
Lấy _id bác sĩ trong kết quả. Hoặc lấy ID từ GET /api/doctors nếu đã có dữ liệu.

Tạo token bác sĩ (thay ID thật, bỏ dấu < >):
  npm run token -- doctor <doctorId>

Với API cần đăng nhập, thêm header:
  Authorization: Bearer <token>
  Content-Type: application/json

Không dùng x-role hay x-doctor-id để phân quyền. Bác sĩ được nhận diện bằng doctorId
trong token đã ký. Admin quản lý tất cả bác sĩ; bác sĩ chỉ quản lý dữ liệu của mình.
API tạo bác sĩ cũ nay yêu cầu admin; API danh sách lịch hẹn cũ nay trả phân trang
và yêu cầu admin. Frontend cũ gọi các API này cần gửi token và đọc đúng cấu trúc mới.

3. Tám API trong yêu cầu

(1) GET /api/schedules
  Bác sĩ: chỉ thấy ca của mình. Admin: thấy tất cả, lọc ?doctor=<doctorId>.
  Có thể lọc thêm ?date=YYYY-MM-DD. Trả về một mảng ca làm việc.

(2) POST /api/schedules
  Body: { "doctor": "<doctorId>", "date": "2027-01-04",
          "startTime": "08:00", "endTime": "11:30" }
  Bác sĩ có thể bỏ trường doctor, server tự lấy ID từ token. Admin phải gửi doctor.
  Thành công trả 201 và ca vừa tạo. Một ngày có thể có nhiều ca không trùng nhau.
  Ca phải ở tương lai; thời lượng chia hết cho 30 phút; không hỗ trợ ca qua nửa đêm.
  Ví dụ 08:00–11:30 và 13:30–16:30 là hai bản ghi ca riêng.

(3) PUT /api/schedules/:id
  Body: { "startTime": "08:30", "endTime": "11:30" }
  Có thể đổi date, startTime, endTime; trường không gửi thì giữ nguyên.
  Không đổi bác sĩ của ca. Chặn ca trùng và thay đổi khiến lịch hẹn sắp tới mất slot.
  Hai ca liền nhau như 08:00–09:00 và 09:00–10:00 được phép.

(4) DELETE /api/schedules/:id
  Không có body. Thành công trả 200 kèm thông báo.
  Ca còn lịch pending/confirmed trong tương lai: trả 409, cảnh báo và liệt kê
  details.appointmentIds, details.count; không xóa. Hủy/xử lý các hẹn đó trước.
  Không có chức năng ép xóa hoặc tự động hủy lịch của bệnh nhân.

(5) GET /api/doctors/:id/slots?date=2027-01-04
  Công khai. Bắt buộc có date hợp lệ.
  Ví dụ kết quả:
  { "doctor": "...", "date": "2027-01-04", "slotMinutes": 30,
    "source": "schedule", "slots": ["08:00", "08:30", "09:00"] }
  Có ca trong ngày: dùng đúng các ca đó, không cộng thêm khung mặc định.
  Chưa có ca trong ngày: thứ 2–thứ 7 dùng 08:00–11:30 và 13:30–16:30;
  source là default. Chủ nhật không có slot mặc định, nhưng vẫn được khai báo ca.
  Một slot dài 30 phút: 11:00 là slot cuối buổi sáng; 16:00 là slot cuối buổi chiều.
  Lọc bỏ slot đã có lịch chưa hủy và slot đã qua. Không trả tên/số điện thoại bệnh nhân.
  Xóa ca cuối cùng sẽ quay lại quy tắc mặc định; không có ca không có nghĩa là nghỉ.

(6) GET /api/appointments/doctor?date=2027-01-04&status=pending
  Chỉ bác sĩ. Trả mảng lịch hẹn gửi tới bác sĩ trong token.
  date và status đều không bắt buộc. Không thể dùng doctor query để xem bác sĩ khác.

(7) GET /api/appointments?doctor=<doctorId>&date=2027-01-04&status=pending&page=1&limit=10
  Chỉ admin. Các bộ lọc không bắt buộc; page mặc định 1, limit mặc định 10, tối đa 100.
  Kết quả: { "data": [...], "pagination": {
    "page": 1, "limit": 10, "total": 1, "totalPages": 1 } }

(8) PATCH /api/appointments/:id/status
  Bác sĩ của lịch hẹn hoặc admin.
  Xác nhận: { "status": "confirmed" }
  Hủy: { "status": "cancelled" }
  Hoàn thành: { "status": "completed", "result": "Kết quả khám..." }
  Luồng: pending -> confirmed -> completed.
  pending hoặc confirmed -> cancelled. completed/cancelled là trạng thái cuối.
  Chỉ hoàn thành khi đã đến giờ khám; bắt buộc nhập kết quả không rỗng.
  Không cho ghi kết quả trong thao tác xác nhận/hủy hoặc mở lại lịch đã kết thúc.

4. Đặt lịch để thử slot và cảnh báo

Giữ lại POST /api/appointments công khai từ dự án cũ:
  { "doctor": "<doctorId>", "date": "2027-01-04", "timeSlot": "08:00",
    "patientName": "Trần Minh", "phone": "0901234567", "reason": "Khám định kỳ" }
Server luôn tạo status=pending, bỏ qua status/result client tự gửi lên.
Slot phải ở tương lai, thuộc ca hoặc khung mặc định và chưa có người đặt.
Hủy lịch sẽ trả lại slot. Chỉ xem slot không giữ chỗ; đặt thành công mới giữ chỗ.

5. Đọc code theo thứ tự

src/models/Schedule.ts: cấu trúc ca (bác sĩ, ngày, giờ bắt đầu/kết thúc).
src/models/Appointment.ts: bổ sung completed, result và index chống trùng lịch.
src/middlewares/auth.ts: kiểm tra chữ ký, hạn token và quyền sở hữu.
src/controllers/schedule.controller.ts: danh sách, thêm/sửa/xóa ca, bảo vệ lịch hẹn.
src/services/slots.ts: chia ca thành các slot 30 phút và loại giờ bận.
src/controllers/appointment.controller.ts: lọc, phân trang, đặt hẹn, chuyển trạng thái.
src/utils/time.ts: kiểm tra ngày/giờ, quy đổi giờ khám Việt Nam.
src/services/doctorLock.ts: khóa ngắn để các thao tác cùng bác sĩ chạy lần lượt.
src/routes/: ghép URL với middleware và hàm xử lý.
src/utils/http.ts + middlewares/errorHandler.ts: chuyển lỗi async thành JSON.

Code dùng hàm và vòng lặp trực tiếp, không thêm repository/DI hay kiến trúc nhiều tầng.
Các đoạn kiểm tra quyền, trùng ca, slot và chuyển trạng thái có chú thích tiếng Việt.

6. Kiểm thử và quy ước dữ liệu

  npm run build
  npm test

Test dùng MongoDB tạm riêng qua mongodb-memory-server, không kết nối MONGO_URI
của ứng dụng và không sửa dữ liệu thật. Lần đầu cần mạng để tải MongoDB dùng test.
Cần Node.js 20.19 trở lên (khuyên dùng bản LTS hiện có trên máy).
Các nhóm test bao phủ đủ 8 API, sai quyền, ngày sai, ca trùng, sửa/xóa có hẹn,
khung mặc định, lọc/phân trang, hoàn thành có kết quả và request đồng thời.

Ngày gửi lên luôn YYYY-MM-DD, giờ HH:mm. Ngày lưu MongoDB ở 00:00 UTC như nhãn ngày,
nhưng thời điểm khám thực tế được tính theo UTC+7 (Việt Nam).
Nếu dữ liệu cũ lưu date có giờ khác 00:00 UTC, cần chuyển dữ liệu theo ngày khám
đúng trước khi dùng bộ lọc này. Không tự động thay đổi dữ liệu cũ trong bài.

Index duy nhất yêu cầu không có lịch trùng doctor/date/timeSlot chưa hủy.
Nếu DB cũ có dữ liệu trùng, hãy kiểm tra, xử lý bản ghi trùng trước khi chạy server;
không xóa DB để sửa lỗi index. Server chờ tạo index xong mới mở cổng.

Khi request đồng thời trên cùng bác sĩ, request đang bận có thể trả 409 để client thử lại.
Khóa MongoDB được bỏ trong finally sau mỗi thao tác. Nếu tiến trình bị tắt đột ngột
đúng lúc đang giữ khóa, khóa có thể còn lại. Chỉ khi đã DỪNG TẤT CẢ server đang dùng
DB này mới dùng mongosh để bỏ khóa bị kẹt, thay ID thật:
  db.doctors.updateOne({_id: ObjectId("<doctorId>")}, {$unset: {scheduleLock: ""}})
Không bỏ khóa khi server còn đang xử lý request. Đây là giải pháp đơn giản cho bài
sinh viên; triển khai nhiều máy thực tế cần cơ chế khóa/giao dịch và phục hồi đầy đủ.

Xem thêm requests.http để chạy nhanh từng bước bằng extension REST Client của VS Code,
hoặc chép các request sang Postman. Hãy chọn ngày trong tương lai khi thử.
